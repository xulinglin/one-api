# sub2api 二次开发指南

> 面向本仓库（Go 后端 + Vue3 前端 + PostgreSQL + Redis）的二开说明。
> 重点：**理解请求链路** 与 **接入新的上游平台 / provider**。
> 所有路径均相对仓库根目录，`file:line` 为当前版本的实际位置，升级后可能偏移，按函数名检索即可。

---

## 1. 技术栈与目录地图

| 层 | 技术 | 位置 |
| --- | --- | --- |
| 后端 | Go 1.2x + Gin + ent + go-redis + viper | `backend/` |
| 依赖注入 | Google Wire（生成代码已提交） | `backend/cmd/server/wire_gen.go` |
| 前端 | Vue 3 + Vite + Pinia + Tailwind | `frontend/` |
| 前端产物 | 构建进 `backend/internal/web/dist`，再通过 `-tags embed` 打进二进制 | `backend/internal/web/` |
| 数据库 | PostgreSQL | 表结构由 ent + `backend/migrations` 管理 |
| 缓存/队列/限流 | Redis | `backend/internal/repository/redis.go` |

后端 `internal/` 关键目录：

```
domain/        平台与账号等"领域常量/注册表"（扩展的第一站）
pkg/           各上游协议客户端（openai / claude / gemini / geminicli / antigravity / xai / apicompat ...）
service/       业务层：调度、计费、账号、网关转发（大量 *_gateway_*.go）
handler/       HTTP 层：网关 handler + admin handler
server/routes/ 路由注册（gateway.go / admin.go / auth.go / user.go）
server/middleware/ 鉴权、限流、分组模型白名单等
repository/    数据访问 + Redis 缓存实现，wire 提供者
config/        config.yaml 映射 struct 与默认值
web/           前端静态资源与 embed 开关
```

## 2. 本地运行与构建

### 2.1 依赖服务（缺一不可）

- **PostgreSQL**：硬依赖，连不上直接启动失败。
- **Redis**：虽为懒连接（`repository/redis.go:23` 的 `InitRedis` 只创建 client 不 ping），服务能起来，但**限流中间件是 fail-close**，Redis 不在时登录/注册/网关会直接 `429`，实际不可用。

本机便携版的启动命令：

```powershell
& f:\ide\_deps\pgsql\pgsql\bin\pg_ctl.exe -D f:\ide\_deps\pgdata -l f:\ide\_deps\pg.log start
f:\ide\_deps\redis\redis-server.exe --port 6379
$env:DATA_DIR="f:\ide\sub2api\run"; f:\ide\sub2api\sub2api.exe
```

### 2.2 改完代码后的构建顺序

前端必须先构建，后端才能 embed 到二进制：

```powershell
cd f:\ide\sub2api\frontend
pnpm install
pnpm run build          # 产物 -> backend/internal/web/dist

cd f:\ide\sub2api\backend
go build -tags embed -o ..\sub2api.exe .\cmd\server
```

- 只改后端 → 直接 `go build`。
- 只改前端 → 前端构建后必须重新 `go build -tags embed`，否则二进制里还是旧页面。
- 不带 `embed` 标签时，前端走磁盘目录，适合边改边看（需要另开 Vite dev server）。

### 2.3 运行时数据

`DATA_DIR`（默认 `run/`）下是 `config.yaml`、`logs/`、上传与 TOTP 密钥等。`run/config.yaml` 里的 JWT secret、数据库密码、加密密钥**不要随意重置**，否则历史 token / 已加密凭据会失效。

## 3. 请求主链路（理解二开的关键）

一次 `/v1/chat/completions`、`/v1/messages` 或 Gemini 兼容请求，按下面顺序流转：

### 3.1 路由与中间件

入口：`backend/internal/server/routes/gateway.go:22` `RegisterGatewayRoutes`。

中间件顺序（同一文件，`gateway.go:36-47` 定义、下方注册）：

```
RequestBodyLimit → ClientRequestID → InboundEndpointMiddleware
→ apiKeyAuth（校验 sk- key，定位 user + group + platform）
→ RequireGroupAssignment（未分组拒绝，按协议输出不同错误体）
→ GroupModelAllowlist（按客户端书写的模型名做分组白名单）
→ compositeTargetPlatformMiddleware（composite 分组解析真实目标平台）
→ 具体 gateway handler
```

要点：**平台信息来自 API Key 绑定的分组**（`getGroupPlatform(c)`），而不是请求体里的模型名。二开要新增平台时，先确保该平台能作为分组平台登记（见第 5 节）。

### 3.2 按"网关族"分派，而不是按平台逐个写路由

平台清单里每个平台声明自己归属哪个网关族：`domain/platforms.go:10-22`

```go
PlatformGatewayAnthropic   // Claude Messages 协议 + TypeSafe /v1/systemone
PlatformGatewayOpenAI      // OpenAI、Grok 及所有"多协议 API Key 供应商"
PlatformGatewayGemini      // Gemini 兼容网关
PlatformGatewayAntigravity // Antigravity 网关
```

路由层用它做分派，例如：

- `gateway.go:49-52` `UsesOpenAIGateway(platform)` → OpenAI 网关
- `gateway.go:54-61` `CountTokens` 按平台选 handler
- `gateway.go:76-91` `/images` 只对 openai / grok 放行

所以二开时**优先复用已有网关族**：只要新上游说 OpenAI Chat Completions 或 Responses 协议，挂到 `PlatformGatewayOpenAI` 即可，无需新写一套 handler。

### 3.3 Handler → 业务层

- OpenAI 族：`handler/openai_gateway_handler.go`（构造入口 `:352`）
- Anthropic 族：`handler/gateway_handler.go`（平台分支示例 `:1471`、`:1482`）

Handler 负责：解析请求体、鉴权上下文、并发槽位申请、调用 `service`、把上游流式响应转成客户端协议、最后触发计费。

### 3.4 选号与调度

调度是"按分组 → 平台 → 可用账号"的过程：

- 通用调度：`service/gateway_scheduling.go`
- OpenAI 族：`service/openai_gateway_scheduling.go`、`service/openai_account_scheduler.go`
- 冷却/阈值评估：`service/account_scheduling_threshold_eval.go`
- 快照与 Redis 缓存：`service/scheduler_snapshot_service.go`、`service/scheduler_cache.go`

选号依赖账号上的 `platform / type / status / schedulable / proxy_id` 与分组绑定关系；失败会触发换号（failover）与冷却。

### 3.5 转发与协议转换

- 转发主逻辑：`service/openai_gateway_forward.go`（按 `account.Platform` 做字段级适配，示例 `:583-620`）
- 跨协议桥接：`pkg/apicompat/`（ChatCompletions ↔ Anthropic ↔ Responses）
- 各上游客户端：`pkg/openai`、`pkg/claude`、`pkg/gemini`、`pkg/geminicli`、`pkg/antigravity`、`pkg/xai`

上游地址解析统一在账号模型上：

| 方法 | 用途 | 位置 |
| --- | --- | --- |
| `GetBaseURL()` | Anthropic 协议默认地址 | `service/account.go:1090` |
| `GetOpenAIBaseURL()` | OpenAI 协议默认地址 / 凭证覆盖 | `service/account.go:1509` |
| `GetCNProtocolBaseURL()` | 国产供应商按协议取地址 | `service/account.go:1606` |
| `GetOpenAIFormatBaseURL()` | OpenAI 格式端点用 | `service/account.go:1654` |
| `GetGrokBaseURL()` | Grok 专用 | `service/account.go:1753` |

### 3.6 计费与日志

- 统一计价入口：`service/billing_service.go:1562` `CalculateCostUnified`
- 旧路径：`:1863` `CalculateCost` / `:2047` `CalculateCostWithConfig`
- 余额缓存扣减：`service/billing_cache_service.go:372` `DeductBalanceCache`
- 计费依赖的定价来自 **分组上的模型价格表**（`service/group.go:62` 附近、`service/billing_service.go:2124`），与平台解耦。新增平台若沿用现有模型名，通常**不需要**改计费代码。

## 4. 平台注册表（扩展的核心）

`backend/internal/domain/platforms.go` 是"所有平台"的**单一数据来源**（文件头注释已说明）。新增平台只需在 `platformList`（`:37-51`）追加一条：

```go
{ID: PlatformMyProvider, DisplayName: "My Provider", Gateway: PlatformGatewayOpenAI, LiteLLMProvider: "openai"},
```

字段含义：

- `Gateway`：归属哪个网关族（决定走哪套 handler/转发）。
- `CNProvider`：是否共享国产供应商的余额 / Coding Plan 探测能力。
- `LiteLLMProvider`：定价目录里的 provider 名，留空表示不从定价目录同步模型。

登记后，以下能力会自动包含它（注释 `:3-8` 明确写了）：

- 分组可选平台列表、用户额度、组合路由目标、调度快照、定价匹配
- `UsesOpenAIGateway()`（`:128`）、`IsConcretePlatform()`、`CompositePrecedencePlatformIDs()`（`:110`）

**仍需要显式改的地方**（注释 `:7-8` 也提示了）：OAuth 流程、渠道监控、余额/Coding Plan 探测、用量窗口、Codex 模型目录。

## 5. 接入一个新上游的两条路线

### 路线 A：OpenAI 兼容上游（推荐，改动最小）

适用：上游提供 `/v1/chat/completions` 或 `/v1/responses`，用 API Key 鉴权（DeepSeek、Kimi、GLM、各类中转站都属此类）。

现有同类实现：`kimi / zhipu / deepseek / minimax / opencode_go / command_code / cline`。

改动清单：

1. **平台常量**：`backend/internal/domain/constants.go:20-42` 加 `PlatformXXX = "xxx"`。
2. **注册表**：`backend/internal/domain/platforms.go:37-51` 追加 `PlatformSpec`，`Gateway` 填 `PlatformGatewayOpenAI`。
3. **前端内置清单**：`frontend/src/constants/platformCatalog.builtin.json` 同步追加条目。
   > 该文件由 `backend/internal/service/platform_catalog_test.go:123` 的 `TestFrontendBuiltinPlatformCatalogInSync` 校验一致性，**必须同步**，否则测试失败。
   > 与其手改，推荐用 `UPDATE_PLATFORM_CATALOG=1 go test -tags unit ./internal/service/ -run TestFrontendBuiltinPlatformCatalogInSync` 从后端注册表重新生成。
4. **默认地址与协议规则**（按需）：
   - 若上游有固定官方端点，在 `service/account.go` 的 `defaultProviderBaseURL` 相关逻辑中补一条（参考 `:1606`、`:1634`、`:1699` 附近的 coding plan 识别）。
   - 若上游同时支持多种协议，在 `frontend/src/constants/platformCatalog.ts` 的 `ProviderProfileInfo`（`:31-48`）与后端对应 profile 里声明 `modes / base_urls / protocol_rules`。
5. **账号凭据**：`type=apikey`（或 `upstream`）+ `credentials.api_key` + `credentials.base_url`。不需要新表、不需要新迁移。
6. **模型映射/定价**：沿用现有模型名即可；若要参与 Model Plaza，给 `LiteLLMProvider` 填上对应 provider 名。
7. **管理端表单**：平台下拉来自前端 catalog，一般自动出现；若该平台有专属字段（如 `account_mode`），参照 `frontend/src/views/admin/AccountsView.vue` 中 kimi/zhipu 的条件渲染补一段。

验证：`go build -tags embed` → 后台新建账号 → 点「测试」→ 用真实 key 发一次请求。

### 路线 B：原生协议 / OAuth 新网关（改动大）

适用：上游只有私有协议，或需要 OAuth 登录（Codex、Gemini CLI、Antigravity、Grok 这类）。

改动清单（按依赖顺序）：

1. **客户端包**：`backend/internal/pkg/<provider>/`，封装鉴权、刷新 token、请求构造、SSE 解析。
2. **平台登记**：`domain/constants.go` + `domain/platforms.go`，`Gateway` 选一个已有族或新增 `PlatformGateway` 值。
3. **新网关族（仅当协议与现有三种都不同）**：
   - `service/<provider>_gateway_forward.go`（转发 + 协议转换）
   - `handler/<provider>_gateway_handler.go`（HTTP 入口）
   - `server/routes/gateway.go` 增加分支（参考 `:53-91` 的写法）
4. **依赖注入**：在 `backend/cmd/server/wire.go` 增加 provider，执行 `wire` 生成 `wire_gen.go`（生成代码已提交，别手改 `wire_gen.go`）。
5. **调度分支**：若账号特性与现有平台不同（例如并发槽位、冷却原因、订阅窗口），在 `service/*_scheduling*.go` 与 `account.IsXxx()`（`service/account.go:276-303`）补判断。
6. **用量归一化**：上游 usage 字段要映射成内部 `UsageTokens`，否则计费为 0。计费入口见 `billing_service.go:1562`。
7. **渠道监控 / 余额探测**：`service/channel_monitor_quota_fetcher.go:218`、`service/channel_monitor_validate.go:219` 都有 `switch account.Platform`，新平台不补就在监控里显示"不支持"。
8. **前端表单**：`frontend/src/views/admin/AccountsView.vue` + `frontend/src/api/admin/accounts.ts`，OAuth 类型还需要授权回调页（参考 Antigravity 的 `api/admin/antigravity.ts`）。

## 6. 账号模型与凭据约定

关键字段（`accounts` 表 / `service.Account`）：

| 字段 | 说明 |
| --- | --- |
| `platform` | 必须是 `domain/platforms.go` 已登记的值 |
| `type` | `oauth / setup-token / apikey / upstream / bedrock / service_account`（`domain/constants.go:64-70`） |
| `oauth_type` | 仅 OAuth 账号使用（如 `google_one`），决定刷新与鉴权实现 |
| `credentials` | JSON，字段随平台不同：`api_key`、`base_url`、`access_token`、`refresh_token`、`project_id`、`account_mode`、`api_protocol` 等 |
| `extra` | 运营性配置：`privacy_mode`、模型映射、tier 等 |
| `proxy_id` | 绑定的出站代理；不绑则直连 |
| `schedulable / status` | 调度开关与健康状态 |

新增凭据字段时：**只加 JSON key，不改表结构**，并在 `service/account.go` 里加对应的 getter（参考 `GetCNAPIKey`、`GetOpenAIBaseURL`），避免散落魔法字符串。

## 7. 常见坑（本机实测记录）

1. **代理只对绑定它的账号生效**。代理管理里加 `http://127.0.0.1:7897` 后，必须到账号编辑页选中该代理，否则仍直连。
2. **限流 fail-close**：Redis 不可用时登录直接 429，日志关键字 `[RateLimit] redis error ... mode=fail-close`。
3. **Gemini `google_one` 账号报 403 `SUBSCRIPTION_REQUIRED`（#3501）**：这是 Google Code Assist 侧的许可判定，不是网络问题。`loadCodeAssist` 当前返回 `allowedTiers=[standard-tier]` 且提示迁移到 Antigravity；走美国代理不能改变账号地区。要么改用 Antigravity OAuth，要么改用 AI Studio API Key。
4. **`refresh-tier` 500 `drive API error: 403`**：OAuth token 缺 Drive scope，google_one 的 tier 探测依赖 Drive API。
5. **Codex 账号测试会报模型不支持**：测试接口 `POST /api/v1/admin/accounts/:id/test`（`handler/admin/account_handler.go:1291`）在不传 `model_id` 时用平台默认测试模型（实测 Codex 账号取到 `gpt-5.4`），而 ChatGPT 账号可能只支持特定 Codex 模型，于是报 `The 'gpt-5.4' model is not supported when using Codex with a ChatGPT account`。这是**测试默认模型的问题**，不代表账号不可用；传 `{"model_id":"<账号实际支持的模型>"}` 或发真实请求验证。
6. **改深色主题别只改 Tailwind 色板**：`frontend/src/components/common/DataTable.vue` 等文件里有硬编码的 `rgb(31 41 55)` 表头/sticky 列颜色，优先级高于工具类，改色板不会生效。
7. **前端改了看不到效果**：忘了 `go build -tags embed`，或浏览器缓存（Ctrl+F5）。

## 9. 建议的二开顺序

1. 先只做**路线 A**（OpenAI 兼容），把平台登记 + 账号 + 测试跑通，确认计费与日志正确。
2. 需要 OAuth / 私有协议时再动**路线 B**，并且优先复用现有网关族（`PlatformGatewayOpenAI` 能覆盖绝大多数"协议兼容"场景）。
3. 每加一个平台，同步：`domain/platforms.go` → `platformCatalog.builtin.json` → 账号表单 → 监控分支。少同步一处就会出现"后台能建号但监控空白"或"分组选不到平台"。
